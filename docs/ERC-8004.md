# Tessera, ERC-8004 and the Solana Agent Registry

ERC-8004 ("Trustless Agents") gives an agent an identity and a place where others can leave feedback
about it. The Solana Foundation ships the same thing on Solana as the
[Agent Registry](https://solana.com/agent-registry). Tessera does not replace either. It adds the part
they leave out: **what happens to the money.**

This page says what the standard covers, what it says it does not cover, and how Tessera plugs in. The
bridge described here is live on devnet; the addresses are in
[`deployments/registry.json`](../deployments/registry.json).

## What ERC-8004 covers, in its own words

Quotes are from the ERC text (`ethereum/ERCs`, `ERCS/erc-8004.md`, status Draft, read 5 October 2026).

| Topic | What the standard says |
|---|---|
| Payments | "Payments are orthogonal to this protocol and not covered here. However, examples are provided showing how x402 payments can enrich feedback signals." |
| Fake reviews | "Sybil attacks are possible, inflating the reputation of fake agents. The protocol's contribution is to make signals public and use the same schema." |
| Scoring | "While simple filtering by reviewer (useful to mitigate spam) and by tag are enabled on-chain, more complex reputation aggregation will happen off-chain." |
| Proof of payment | An optional `proofOfPayment` object in the off-chain feedback file. |

The discussion thread says the same thing more bluntly. Two posts from
[the Ethereum Magicians thread](https://ethereum-magicians.org/t/erc-8004-trustless-agents/25098)
(the first four pages of the thread were read as plain text and searched for this page; not every post was read):

- Post 94, 13 Oct 2025, on the rule that a reviewer had to be pre-authorised: "this does not solve the
  Sybil/spam problem".
- Post 136, 21 Apr 2026: "An agent can create fake clients and leave itself glowing reviews. There's no
  financial cost to having a bad reputation and no financial consequence for poor performance."

On Solana, the Agent Registry lists its own prices: registering an agent costs about 0.009 SOL and
leaving feedback costs 0.00001 SOL (solana.com/agent-registry, read 5 October 2026). Feedback there does
not require a purchase. The registry has an optional scoring engine (ATOM) and a "ProofPass" flow for
feedback the agent itself requested; both are the registry's own answers to the same problem.

## What Tessera adds

| | ERC-8004 / Agent Registry | Tessera |
|---|---|---|
| Who can review | Anyone with a wallet | Only the two parties of an order that was paid into escrow and settled |
| Weight of a review | One review, one entry | Settled amount × the reviewer's tier weight, capped per counterparty |
| Where the score is computed | Mostly off-chain, by whoever wants to | On-chain, integer arithmetic, the same code in the program, the SDK and the site |
| What a score changes | Nothing by itself; it is a signal to read | How long a payment is held in escrow, and how much a merchant may take without a hold |
| Cost of a bad record | A lower number | Longer holds on every order, and a penalty that only time removes |
| Payments | Out of scope | The core: x402 `exact` payments land in a per-order escrow |

The two fit together. The registry answers "who is this agent and where is its endpoint". Tessera
answers "should my money wait, and for how long".

## The bridge that is live on devnet

`npm run registry` (source: [`scripts/registry.ts`](../scripts/registry.ts)) does four things for each
merchant agent, using the registry's published SDK (`8004-solana`):

1. **Registers the agent** in the Agent Registry. The registration file follows the ERC-8004
   `registration-v1` shape and declares `x402Support: true` and the trust models `reputation` and
   `crypto-economic`. It is served from this repository
   ([`deployments/registry/`](../deployments/registry)).
2. **Sets the agent wallet** on the registry asset to the same wallet that owns the Tessera credit file.
   Given a Tessera wallet, the registry's own lookup (`getAgentByWallet`) returns the registry identity.
3. **Writes the Tessera credit file's address** into the asset's on-chain metadata under the key
   `tessera`. Given a registry identity, one read returns the credit file.
4. **Mirrors reviews** (`--mirror N`). Each copied review is a registry feedback entry signed by the
   buyer, with:
   - `tag1`: `x402-resource-delivered` for 3 stars or more, `x402-quality-issue` for less. These are
     the registry's own x402 tags.
   - `tag2`: `exact-svm`.
   - `value`: the order amount in USDC (6 decimals); `score`: stars × 20.
   - `feedbackUri`: the Tessera review account. That account can only be created by the program after
     the order settled, so it is the proof of payment.

## What this does not do

- The mirrored reviews come from this project's own buyer agents. The registry cannot tell that, and it
  does not need to: that is the sybil problem the standard describes. Tessera's score is what discounts
  them (tier weights, a per-counterparty cap, time gates). See [SCORING.md](SCORING.md).
- The registry's own aggregate (ATOM) was switched on for these four agents after the first 12 copies,
  so it counts 4 of the 7 mirrored reviews per agent. It reported an average score of 15.97 after those
  four 100-point entries. That is the registry's engine being cautious with a new agent; we did not
  investigate its formula.
- The registration files point at `http://localhost:4020`, because the demo agents run from this
  repository. A hosted deployment would update the URI with `setAgentUri`.
- The mirror is a script, not part of the program. Tessera's program does not call the registry, and
  the registry does not call Tessera. Nothing in the score depends on the registry.
- Buyers are not registered. Merchant-to-buyer feedback (`x402-good-payer`) needs the buyer to have a
  registry identity.
- No theorem makes this sybil-proof. Cheng and Friedman showed in 2005 ("Sybilproof reputation
  mechanisms", ACM SIGCOMM P2PECON workshop) that no reputation function that treats all nodes
  symmetrically is sybil-proof. Tessera's score is symmetric in that sense. What it does is put a price
  on the attack, in fees and in time, and bound what a faked record can take. Those numbers are in
  [SECURITY.md](SECURITY.md).
